## 🔥 Troubleshooting

### 1. 1.1만 건 제품 대상 유사 상품 추천 검색 성능 개선

#### ❗ 문제 상황

- 약 1.1만 건의 제품 중 두피 진단 결과와 비슷한 상품을 찾아 추천하는 검색 API가 필요
- **정확도를 높이면 속도가 느려지고, 속도를 높이면 정확도가 떨어지는 트레이드오프** 존재
- 기존 SQL 기반 조회로는 원하는 벡터 유사도 검색을 구현하기 어려워 정확도가 떨어짐

#### 🛠️ 해결 과정

| 단계 | 시도 | 결과 |
| :---: | :--- | :--- |
| 1 | Elasticsearch에 제품 임베딩을 저장하고 `script_score` 방식으로 벡터 유사도 검색 구현 | ⚠️ 전수 탐색 구조라 SQL보다 **약 4배 느려짐** |
| 2 | 성능 저하를 해결하기 위해 **HNSW 기반 kNN 검색**으로 변경 | ⚠️ 사용 중인 Elasticsearch 공식 Java 클라이언트 버전에서 `KnnQuery` 미지원 |
| 3 | **Low-Level REST Client**로 JSON 형식 쿼리를 직접 전송 | ✅ 해결 |

- 나중에 라이브러리를 업데이트할 때 쉽게 교체할 수 있도록 요청/응답 파싱 로직을 모듈화해 기술 부채 최소화

#### ✅ 결과

- 검색 응답 시간: 기존 SQL 기반 조회 대비 **약 3배 단축**
- Top-k 검색 결과에서 진단 키워드와 관련된 상품 비중 **약 2배 증가**

<br/>

### 2. 외부 API 순차 호출로 인한 응답 지연 개선

#### ❗ 문제 상황

- 위치 기반 날씨 정보에 맞춰 두피 관리법을 제공하는 기능에서 외부 API 3개를 순차 호출
- 응답까지 **6.1초**가 걸려 사용자 경험을 해침

#### 🛠️ 해결 과정

**① `CompletableFuture`로 3개 API 병렬 호출**

- 3개의 API를 비동기로 병렬 처리하고, `allOf()`로 모두 완료될 때까지 대기
- 가장 오래 걸리는 API의 응답 시간만큼만 기다리면 되므로 전체 대기 시간이 줄어듦

**② Redis 캐싱으로 같은 지역 요청은 즉시 반환**

- Redis 캐싱 적용: 모든 서버 인스턴스가 하나의 캐시를 공유하므로, 시스템 전체 기준으로 외부 API 호출을 최소화할 수 있음
- `@Cacheable` 적용: 캐싱을 선언적으로 적용해 비즈니스 로직 코드를 깔끔하게 유지

#### ✅ 결과

- 날씨 기반 API 응답 속도 **4.6배 개선 (6.1초 → 1.5초)**
- 같은 지역의 반복 요청은 Redis Cache Hit 시 **약 4ms**

> 💡 이후 코드를 다시 검토하면서, 같은 클래스 내부에서 호출하면 `@Cacheable` Proxy가 적용되지 않는 **self-invocation 문제**를 발견했습니다.
> Scheduler와 Cache 책임을 별도 Bean으로 분리하는 방향으로 개선을 검토했습니다.
