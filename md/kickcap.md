## 🔥 Troubleshooting

### 1. 경찰 · 시민 사용자별 인증 구조 설계

#### ❗ 문제 상황

- 경찰과 시민은 같은 서비스를 사용하지만 **인증 방식, 접근할 수 있는 데이터, 사용할 수 있는 기능이 서로 다름**
- 하나의 사용자 구조로 처리하기보다, 인증 방식과 사용자 유형을 명확히 구분해야 한다고 판단

#### 🛠️ 해결 과정

**① 역할별 인증 흐름 분리**

- 경찰: 일반 로그인
- 시민: OAuth2 기반 소셜 로그인
- 서로 다른 로그인 방식을 하나의 JWT 인증 구조 안에서 구분할 수 있도록 **사용자 타입별 인증 흐름** 설계

**② 다중 기기 로그인을 위한 Token 관리 구조**

- 다중 기기 로그인 환경에서 알림 대상을 구분할 수 있도록 FCM Token 정보를 별도 테이블로 분리
- 기기별 FCM Token과 Refresh Token을 매핑해 관리하는 `DeviceInfo` 구조 설계

**③ 경찰 대시보드 동적 조회**

- 지역·기간 등 여러 조건을 조합해 조회할 수 있도록 QueryDSL 기반 동적 조회 API 구현

#### ✅ 결과

- 로그인 방식이 다른 경찰과 시민을 사용자 타입별로 구분하면서도, **인증 이후에는 JWT 기반 공통 인증 흐름**으로 처리하는 구조 완성
- 기기별 Token 관리 구조로 다중 기기 로그인과 알림 Token을 관리
- QueryDSL로 여러 조회 조건이 결합되는 경찰 대시보드 API 구현

### 2. 법률 상담 챗봇의 답변 신뢰도 문제 → RAG 파이프라인 구축

#### ❗ 문제 상황

- GPT API만 연결해서는 프로젝트에서 가정한 **킥보드 관련 법률에 맞는 답변을 안정적으로 제공하기 어려움**
- PDF 법률 문서를 그대로 파싱하면 줄바꿈·특수문자 때문에 데이터 품질이 떨어지고, **질문과 관계없는 조항이 검색되는 문제** 발생
- 외부 지식을 검색해 답변에 활용할 수 있도록 **RAG 파이프라인을 직접 설계**하기로 결정

#### 🛠️ 해결 과정

**HuggingFace 임베딩 + FAISS Index 기반 RAG 파이프라인 구성**

| 단계 | 내용 |
| :--- | :--- |
| 전처리 | NAVER Clova OCR로 PDF를 다시 처리해 임베딩에 쓸 문서 품질 개선 |
| Chunking | `RecursiveCharacterTextSplitter`로 문맥을 고려해 문서 분할 |
| Embedding | `ko-sroberta-multitask`로 한국어 법률 문서 임베딩 |
| Indexing | 가볍고 유사도 검색이 빠른 FAISS Index 구축 |
| Retrieval | 사용자 질문을 벡터화한 뒤 `similarity_search(k=5)`로 유사 조항 검색 |
| Generation | 검색된 Context와 질문을 GPT Prompt에 전달해 답변 생성 |

- Prompt에 역할·답변 형식·예시·규칙을 명시
- 법률과 관련 없는 질문에는 안내 메시지를 반환하도록 분기 처리

#### ✅ 결과

- OCR 기반 데이터 전처리로 **질문과 관계없는 조항이 검색되는 문제를 줄이고**, 프로젝트에서 정의한 법률 정보를 검색해 답변에 활용하는 RAG 흐름 구현
- 미리 정한 질문 목록을 기준으로 Prompt 구성 요소를 바꿔 가며 응답을 반복 비교해, 검색된 정보가 답변에 제대로 반영되는지 직접 검증하고 개선
